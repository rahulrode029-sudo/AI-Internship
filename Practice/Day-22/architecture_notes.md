# Multi-Agent AI Research Assistant - Architecture Notes

## 1. Introduction

The Multi-Agent AI Research Assistant is designed using a modular multi-agent architecture.

The main idea is to divide a complex research task into multiple smaller responsibilities. Each responsibility is handled by a specialized AI agent.

The system contains five agents:

```text
Coordinator
Research Agent
Analyzer
Critic
Writer
```

These agents communicate using a shared state managed through a LangGraph workflow.

## 3. Architecture Components

### 3.1 User Layer

The user provides a research question.

Example:

```text
What are the advantages and challenges of AI in education?
```

The question is passed to the Coordinator.

---

## 3.2 Coordinator Layer

The Coordinator is responsible for controlling the workflow.

It creates the research plan and starts the Research Agent.

The Coordinator does not perform all research itself. Instead, it delegates work to specialized agents.

---

## 3.3 Research Layer

The Research Agent is responsible for collecting relevant information.

It receives:

```text
User Query
Research Plan
```

and produces:

```text
Research Results
```

The results are stored in the shared state.

---

## 3.4 Analysis Layer

The Analyzer receives the research results and processes them.

Its responsibilities include:

* Organizing information.
* Identifying important findings.
* Removing irrelevant information.
* Comparing information.
* Identifying limitations.
* Producing structured analysis.

---

## 3.5 Critic Layer

The Critic is responsible for quality control.

The Critic evaluates the Analyzer's output.

There are two possible outcomes.

### Approval

```text
Critic → Writer
```

### Revision Required

```text
Critic → Analyzer
```

The Analyzer then improves the analysis.

A maximum revision limit is used in the implementation to prevent an endless loop.

---

## 3.6 Writer Layer

After the Critic approves the analysis, the Writer creates the final response.

The Writer receives:

```text
User Query
Analysis
Critic Feedback
```

and generates:

```text
Final Answer
```

---

## 4. Shared State Architecture

The system uses a shared state to exchange information between agents.

The state contains:

```text
user_query
research_plan
research_results
analysis
critic_feedback
revision_count
final_answer
workflow_status
```

### State Flow

```text
User Query
    ↓
Research Plan
    ↓
Research Results
    ↓
Analysis
    ↓
Critic Feedback
    ↓
Final Answer
```

The shared state makes it possible for later agents to access information generated by earlier agents.

---

## 5. Communication Architecture

The communication between agents is controlled by the LangGraph workflow.

The main communication path is:

```text
Coordinator
    ↓
Research Agent
    ↓
Analyzer
    ↓
Critic
    ↓
Writer
```

The feedback communication path is:

```text
Critic
   |
   | Revision Required
   v
Analyzer
   |
   v
Critic
```

This creates a quality-control loop.

---

## 6. Workflow Control

LangGraph is used to define the workflow.

The graph contains nodes representing agents:

```text
coordinator
researcher
analyzer
critic
writer
```

Edges define communication between these nodes.

The Critic uses conditional routing:

```text
IF APPROVED
    ↓
Writer

IF REVISION REQUIRED
    ↓
Analyzer
```

A maximum revision count prevents the system from repeatedly looping between the Analyzer and Critic.

## 7. Technology Architecture

The technology stack consists of:

```text
Python
   |
   +-- LangChain
   |
   +-- LangGraph
   |
   +-- Google Gemini
   |
   +-- python-dotenv
```

### Python

Used for implementing the complete application.

### LangChain

Used for interacting with the language model.

### LangGraph

Used for creating the multi-agent workflow and conditional routing.

### Google Gemini

Used as the underlying language model for the specialized agents.

### python-dotenv

Used for loading environment variables such as the API key.

---

## 8. Modular Design

Each agent is implemented as a separate Python module.

```text
src/
│
├── state.py
├── llm.py
├── coordinator.py
├── researcher.py
├── analyzer.py
├── critic.py
├── writer.py
└── graph.py
```

This modular design makes the system easier to maintain and extend.

For example, a Web Search Agent can later be added without completely changing the existing agents.

---

## 9. Security Considerations

The Gemini API key is stored in the `.env` file.

Example:

```env
GOOGLE_API_KEY=your_api_key
```

The `.env` file should be included in `.gitignore`.

The API key should never be committed to GitHub.

## 11. Advantages of the Architecture

The architecture provides:

* Clear separation of responsibilities.
* Modular agent design.
* Shared state communication.
* Automated quality checking.
* Conditional workflow execution.
* Feedback-based revision.
* Easy extension with additional agents.
* Better organization of complex AI tasks.

---

## 12. Limitations

The current architecture has some limitations:

1. All agents currently use the same underlying LLM.
2. The Research Agent does not directly access external search engines.
3. Generated information may require external verification.
4. The system does not currently implement long-term memory.
5. API availability and usage limits can affect execution.

## 14. Conclusion

The architecture demonstrates a practical multi-agent AI system in which complex research is divided into specialized tasks.

The Coordinator manages the workflow, the Research Agent collects information, the Analyzer processes it, the Critic validates it, and the Writer generates the final answer.

The shared state and LangGraph workflow provide the communication and control mechanism required to coordinate these agents.
